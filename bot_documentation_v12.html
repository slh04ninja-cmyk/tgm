1. Vue d'ensemble & Architecture

Architecture générale

Telegram (N canaux, dynamique) → Signal Parser → MT5 Bridge → MetaTrader 5 (Exness) ↑ ↓ TimesFM Validator Alertes Telegram (@TrdReport) ↑ ↓ News Manager P&L Quotidien

Principe de fonctionnement

Le bot écoute dynamiquement tous les canaux Telegram configurés dans .env (via TG_CHANNEL_*), parse les signaux de trading (BUY/SELL), et exécute des ordres MARKET sur MetaTrader 5. En v12, le mode est MARKET uniquement — pas de LIMIT, pas de pending orders.

Déduplication — Pourquoi 2 niveaux

ScénarioNiveau 1 (msg_id)Niveau 2 (contenu)
Même message, même ID (reconnexion)✅ Capte—
Même message, ID différent (canal+groupe)❌ Passe✅ Capte
Message édité (même ID, contenu différent)✅ Capte (déjà vu)—
Pourquoi "synchronique, pas d'await" ?
Pas d'entre la vérification et l'enregistrement du msg_id → atomique dans une coroutine asyncio. Si on faisait un await entre les deux, le event loop pourrait exécuter un 2e handler pour le même message.

Structures de déduplication

_seen_msg_ids: dict = {} # message_id → timestamp _seen_messages: dict = {} # (canal_name, hash(texte)) → timestamp _SEEN_TTL = 120.0 # secondes _SEEN_MAX_IDS = 5000 # max entrées

6. Signal Parser

Normalisation du texte

Le parser normalise le texte avant extraction :

  1. Supprime les caractères invisibles (zero-width, espaces insécables)
  2. Convertit les superscripts (¹→1, ²→2...)
  3. Supprime les astérisques (gras Telegram)
  4. Remplace les séparateurs par des espaces
  5. Supprime les emojis
  6. Nettoie les points devant les nombres (.4040 → 4040)
  7. Normalise les paires (XAU/USD → XAUUSD)
  8. UPPERCASE + suppression des préfixes parasites

8. Filtres avant exécution

Chaque signal TRADE passe par une chaîne de filtres. Si un filtre échoue, le signal est rejeté.

Signal TRADE reçu │ ├── ① Filtre News → news_mgr.is_blocked() ? → REJET ├── ② Filtre Horaire → hors 2h-20h UTC ? → REJET ├── ③ Filtre P&L Quotidien → daily_pnl >= 70$ ? → REJET ├── ④ Validation TimesFM → direction prédite ≠ signal ? → REJET │ └── (uniquement signaux TRADE complets, PAS les Quick Alerts) ├── ⑤ Filtre Conflit → même canal + opposé ? → ferme l'ancien ├── ⑥ Symbole MT5 → introuvable ? → REJET ├── ⑦ Prix indisponible → tick None ? → REJET ├── ⑧ SL invalide → BUY: SL >= entry ? → REJET ├── ⑨ Spread trop large → > 50 points ? → REJET ├── ⑩ Max positions → >= 6 actifs ? → REJET └── ✅ EXÉCUTION

Filtre horaire

Bloque les signaux hors de la plage TRADING_START_HOUR (2h) à TRADING_END_HOUR (20h) UTC.

Filtre conflit

Scopé au même canal uniquement — deux canaux différents peuvent avoir des avis opposés sur le même symbole. Si conflit : ferme l'ancien + annule les pending orders.

9. Cas d'exécution des ordres

Signaux Zone → ZN1 ou ZN2

Si le signal zone n'a pas de TP (ex: TP OPEN), le bot génère automatiquement : TP = entry ± TP_FIXED_GAIN_USD (10$).

Signal: BUY 4000 4010 SL 3990 TP 4050 Cas 1 — ZN1 : prix dans [4000, 4010] → MARKET BUY @prix_actuel, lot=0.01, TP=4050, SL=3990 → Commentaire MT5: CH{N}-ZN1 Cas 2 — ZN2 : prix entre zone et SL (meilleur prix) → Prix 3995 (entre SL 3990 et zone 4000) → MARKET BUY → Commentaire MT5: CH{N}-ZN2 Cas 3 — Rejet : prix hors zone → Prix 4020 (au-dessus de la zone) → ANNULÉ

Signaux Prix Unique → PU1 ou PU2

Signal: BUY 4005 SL 3990 TP 4050 PU1 : prix entre entry et SL (meilleur prix) → Prix 3998 → MARKET BUY → Commentaire MT5: CH{N}-PU1 PU2 : prix dans [entry, entry + tolérance] → Prix 4007 (entry 4005 + 2$ < 3$ tolerance) → MARKET BUY → Commentaire MT5: CH{N}-PU2 Rejet : prix > entry + tolérance → Prix 4010 > 4005 + 3$ → ANNULÉ

Quand un nouveau signal arrive d'un canal qui a déjà un signal actif, l'ancien est fermé automatiquement avant d'exécuter le nouveau — même si la direction est identique (ex: BUY 4000 suivi de BUY 4020 → le premier BUY est fermé).

10. Quick Alert (QA)

Déclenchement

Un signal est considéré comme Quick Alert quand :

  • Direction + prix, mais pas de TP/SL complets
  • is_quick_alert=True (défini par le parser)

Exécution

Quick Alert reçue │ ├── Filtres standards (news, horaire, P&L, max positions) ├── Résolution MARKET PRICE (si is_market_price) ├── 1 signal par canal (ferme l'ancien) ├── Vérification tolérance prix (±3$) ├── Filtre distance TP (≥30% restant) ├── Vérification QA existante (mise à jour SL/TP si existe) └── MARKET ORDER → enregistrement + alerte

MARKET PRICE

Si le signal est BUY NOW ou SELL NOW sans prix :

  • Entry = prix actuel
  • SL = entry ± QUICK_ALERT_SL_OFFSET (10$)
  • TP = entry ± SL_OFFSET × RR_RATIO (1.5)

QA existante

Si une QA existe déjà pour le même canal+symbole+direction :

  • Position active → mise à jour SL/TP
  • Position fermée → nouvelle alerte
⚠️ Bug connu — Tolérance SELL inversée :
Le code vérifie current < entry - tolerance pour SELL, ce qui est la direction FAVORABLE (prix baisse = bien pour SELL). Résultat : un SELL dont le prix monte de +4$ (défavorable) passe quand même, tandis qu'un SELL dont le prix baisse de -4$ (favorable) est annulé.
is_unfavorable = current < entry_price - QA_PRICE_TOLERANCE → devrait être current > entry_price + QA_PRICE_TOLERANCE

11. Fusion QA + Signal complet

Principe

Quand un signal complet arrive et qu'un Quick Alert existe déjà pour le même canal+symbole+direction :

Signal complet: BUY 4000-4010 SL 3990 TP 4050 QA existante: BUY @4002 ticket #12345 │ ├── Dans tolérance (±3$) → merge_quick_alert() │ └── SL/TP du QA mis à jour avec ceux du signal complet │ └── Hors tolérance → mise à jour SL/TP quand même └── Pas de fermeture, pas de 2ème position

Fusion dans tolérance

  • Le prix du QA est dans [zone_low - 3$, zone_high + 3$]
  • SL et TP du QA sont mis à jour avec ceux du signal complet
  • Pas de nouvelle position créée

Fusion hors tolérance (OOT)

  • Le prix du QA est hors de la zone de tolérance (±FUSION_TOLERANCE)
  • SL et TP sont quand même mis à jour via bridge.modify_sl_tp()
  • Le signal complet est "absorbé" par le QA — pas de 2ème position
  • Le _is_quick_alert du QA passe à False
  • Une alerte ✏️ FUSION (hors tolérance) est envoyée
Si le QA est déjà fermé (SL/TP touché) : le signal complet est ignoré et une alerte ❌ QA déjà SL/TP est envoyée avec le P&L du QA.

QA déjà fermé

Si le QA a été fermé (SL ou TP touché) avant l'arrivée du signal complet :

  • Le signal complet est ignoré
  • Une alerte est envoyée avec le P&L du QA

12. Gestion BE + Gain fixe

Déclenchement du BE

Chaque 1s — TradeManager._check_all() │ ├── Pour chaque entry active │ ├── Vérifier si _be_activated est False │ ├── _check_pnl_trigger() → min_profit >= PNL_TRIGGER_USD (7$) ? │ │ └── Vérifie whitelist: market_single, quick_market seulement │ └── Si oui → _apply_be_on_open_positions()

Application du BE

ParamètreBUYSELL
SL (BE_USD=3)entry - 3$entry + 3$
TP (TP_FIXED_GAIN_USD=10)entry + 10$entry - 10$
Après le BE : MT5 ferme automatiquement la position quand le prix atteint le TP. Le bot ne fait plus de fermeture manuelle.

Exemple concret

Signal: BUY XAUUSD @4000 Lot: 0.01 1. Prix monte à 4008 → profit = 8$ ≥ PNL_TRIGGER_USD (7$) 2. BE activé: - SL → 3997 (entry 4000 - BE_USD 3) - TP → 4010 (entry 4000 + TP_FIXED_GAIN_USD 10) 3. MT5 ferme à 4010 → profit = 10$ Si le prix redescend à 3997 avant d'atteindre 4010: - SL touché → perte = -3$ (protégé par BE_USD)

Boucle principale

TradeManager._check_all() — toutes les 1s │ ├── _refresh_pos_cache() → mt5.positions_get() │ ├── _check_daily_pnl_limit() │ └── Si atteint → _shutdown_for_daily_limit() │ └── Pour CHAQUE entry dans self.active: │ │ A. DÉTECTION FERMETURE │ ├── _get_pos(ticket) → None si fermé │ ├── _get_last_pnl() → somme deals OUT │ ├── _get_close_reason() → TP / SL / OTHER │ ├── _update_daily_pnl(pnl) │ └── Alerte "🎯 TP" ou "🛑 SL" │ │ B. Position cache

Le cache _pos_cache est rafraîchi une fois par cycle (pas à chaque appel). Réduit le nombre d'appels MT5 de 5-10x par cycle.

Race condition P&L

Un ticket peut se fermer entre la détection et la re-vérification. Le bot exige que TOUS les tickets soient _reported avant de retirer une entry de self.active.

14. P&L Quotidien

Calcul

P&L Quotidien = P&L réalisé + P&L flottant P&L réalisé = somme des deals OUT depuis TRADING_START_HOUR (2h UTC) P&L flottant = somme des profit des positions ouvertes (magic=MAGIC_NUMBER)

Récupération au démarrage

_recover_daily_pnl() récupère le P&L depuis l'historique MT5 (3 derniers jours). Indexe le magic à l'OUVERTURE (pas à la clôture) pour couvrir les fermetures manuelles.

Reset quotidien

Le P&L est reset à TRADING_START_HOUR (2h UTC) chaque jour. Log : RESET JOURNALIER A 2H UTC

Limite quotidienne

Quand daily_pnl + floating >= DAILY_PROFIT_LIMIT (70$) :

  • Toutes les positions sont fermées
  • Tous les pending orders sont annulés (safety net)
  • Le trading est arrêté pour la journée
  • Une alerte est envoyée

15. Filtre News

Fonctionnement

NewsManager │ ├── Fetch (toutes les 30 min, ou au changement de jour) │ ├── GET https://nfs.faireconomy.media/ff_calendar_thisweek.json │ ├── Filtre: impact >= high + pays USD/XAU │ ├── ★ Filtre par JOUR DE TRADING (pas la semaine entière) │ └── Classifie par tier: NFP/CPI, FOMC, Spike, High │ └── Check (toutes les 30s) ├── Pour chaque news DU JOUR: │ ├── diff_minutes = (news_time - now) / 60 │ ├── -after_min <= diff <= close_min → CLOSE positions + BLOCK │ ├── close_min < diff <= block_min → BLOCK seulement │ └── Sinon → UNBLOCK └── _close_all() si should_close

Filtrage par jour de trading

Depuis v12, le bot ne garde que les news du jour de trading en cours (basé sur get_trading_day_start()). L'API ff_calendar_thisweek.json retourne toute la semaine — le bot filtre par date pour éviter les fausses alertes avec des news de jours précédents.

Exemple : Le 31 juillet, les news du 29-30 juillet (FOMC, GDP) ne sont plus affichées ni utilisées pour le filtrage.

16. Validation TimesFM

Principe

TimesFM 2.5 (200M paramètres, Google) prédit la direction du prix sur les 12 prochaines bougies M5. Si la prédiction contredit le signal, celui-ci est rejeté.

Critères de validation

CritèreConditionDéfaut
DirectionPrédiction = direction du signalObligatoire
AmplitudeMove ≥ 5 pipsTIMESFM_MIN_MOVE_PIPS
ConfianceConfiance ≥ 0.35TIMESFM_MIN_CONFIDENCE

Chargement

Le modèle est chargé en arrière-plan (thread daemon) pour ne pas bloquer le démarrage. Si le modèle n'est pas prêt, les signaux passent sans validation.
